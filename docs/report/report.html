LAST MAGAZINE

Assignment 2 report · Taha Keler · Godot 4.7.2 (GDScript) · original 3D game (not a tutorial extension)

1. Game brief

What the player does. LAST MAGAZINE is a first-person survival shooter set in a dark stone labyrinth. The player fights waves of zombies with a pistol, shotgun and rifle whose ammunition is always scarce: every kill refunds a little ammunition, so the player has to keep fighting to keep shooting. A torch, a melee shove and a throwable decoy round out the toolset, and supply caches and medkits are hidden around the map.

Goal and result. In the default mode (Extraction) the player must survive until a 2-minute extraction clock reaches zero; each kill shortens the clock. Win: the clock reaches zero with the player alive ("EXTRACTED"). Loss: health reaches zero ("YOU DIED"). Three more modes reuse the same loop: Timed (survive 5 minutes), Endless (score = survival time) and Signal (arm three relays, then return to the start).

Progress display. The HUD shows the extraction countdown, kills, hostiles alive, health (number and segmented bar), magazine / reserve ammunition, a compass and a minimap. Restart: Play again on the results screen, or Enter at any time, calls Game.start_round(), which resets the player (position, health, stance), the weapons (magazines and reserves), the zombies (all removed, spawner reset), pickups, objectives, timers and counters.

Interaction and collision. Mouse and keyboard drive a CharacterBody3D in 3D. Collisions trigger gameplay responses: the weapon's raycast hitting a zombie's CollisionShape3D applies damage (and kills it at zero), a zombie's lunge that reaches the player's body deals contact damage, and an ammo cache's Area3D detects the player overlapping it (body_entered), which enables its resupply (hold E).

3. The two features

Feature 1 — Ammunition and reload

TriggerLeft click (fire action) and R (reload action); also an automatic reload when the player tries to fire an empty magazine.
State change and ownerThe Weapon node (Player/Head/Camera/Weapon, script src/gameplay/weapon/weapon.gd) owns magazine_ammo and reserve_ammo. try_fire() removes one round; an empty magazine blocks firing and emits dry_fired. try_reload() starts a timed reload (pistol 1.5 s) that moves rounds from reserve to magazine and cannot start with a full magazine or an empty reserve. Kills refund reserve ammunition.
Visible resultThe HUD (src/ui/hud.gd, _on_ammo_changed, _on_reload_started, _on_dry_fired) shows the count, turns it red at 0, shows RELOADING; the weapon model dips and rolls during the reload; a dry-fire click plays.

Supporting mechanic — Player health (loss condition)

Health is the loss condition of the game loop. Trigger: a zombie's lunge reaches the player (Zombie._try_land_hit). State owner: the Health node under Player (src/gameplay/health.gd). Visible result: the health number and segmented bar drop, a red arc points at the attacker, the screen edge pulses red below 35% and, at 0, the round ends with YOU DIED.

4. Corrective prompt log — mouse look did not work

Intended resultMoving the mouse or MacBook trackpad turns the first-person camera (the owner's rule: camera look by mouse or trackpad only, never arrow keys).
Actual resultIn play the camera did not respond to the mouse at all. Every automated test still passed.

Original prompt (owner's requirement, early sessions): camera look must use the mouse or trackpad, never the arrow keys; it must work on a MacBook trackpad. Response: the assistant built Player as a CharacterBody3D with clamped mouse look in _unhandled_input and mouse capture on click (commit "Add first-person player controller"), and later a HUD with a five-part crosshair.

Follow-up prompt 1 (owner, verbatim):

"for the mini map can you jsut get the 2d view of the original map and do it like that, also the mouse doesnt work, fix that immidiatelly and continue on what you where doing"

Response 1 (assistant, verbatim): "Found it. ColorRect defaults to mouse_filter = STOP, and the crosshair's five rects sit dead centre — which is exactly where a captured cursor is pinned. They swallow every InputEventMouseMotion before _unhandled_input ever runs. Every headless test passes because none of them has a cursor sitting over a Control." It then reported: "I verified the geometry (the Dot's rect contains the viewport centre exactly) but I could not reproduce the symptom headlessly … the final word is yours at the keyboard."

Cause. A GUI Control under the cursor consumes mouse events in the GUI phase, and _unhandled_input only receives events nobody consumed. The crosshair's ColorRects used the default MOUSE_FILTER_STOP and sat exactly under the captured cursor, so the player never received mouse motion. The automated tests missed it because headless Godot never hovers a Control.

Fix. Every crosshair rect in src/ui/hud.tscn set to mouse_filter = 2 (IGNORE). A regression test was added (tests/manual/verify_look.gd, test_look_nothing_on_the_hud_swallows_the_mouse) that sends real motion events from the cursor position and fails if any HUD control stops them. Later HUD work (the restyle) was held to the same rule: every new control ignores the mouse.

Follow-up prompt 2 — evidence (owner, verbatim, after playing on the MacBook):

"Its good, the mouse finally works, tho there is a problem, i would prefer that the zombies always run at me …"

The regression test passes in the gate (tools/check.sh, 42 checks, exit 0), and the owner confirmed the fix on real hardware. A second corrected task is in the appendix.

Appendix B — Second corrective case: zombies standing still

Prompt (owner, verbatim): "i would prefer that the zombies always run at me, instead of just staying there in there places"

First result (wrong): the assistant made every spawned zombie keep "catching the player's scent" so that it always heads for the player. A measurement in a real round (Endless mode, 20 zombies, player standing still) showed it did not work: no zombie was unaware any more, but 13 of 20 still stood still while "investigating" 15–23 m away, and the mean distance stayed at 15.0 m after 60 s.

Cause (found by tracing the stuck zombies' navigation agents): the labyrinth's navigation mesh sits up to 0.7 m above the floor a body stands on, and NavigationAgent3D counts a waypoint as reached in 3D against path_desired_distance = 0.6 m. The first waypoint was the zombie's own spot lifted 0.7 m, so it was never reached, and the zombie steered at a point directly above itself at zero speed.

Fix: Zombie._next_waypoint() (src/gameplay/zombie/zombie.gd) measures waypoints on the flat and skips to the first path point that is actually ahead. Evidence: the same measurement afterwards: all 20 zombies within 6 m by 50 s, mean distance 1.4 m; gate exit 0.
